# Data Sourcing Protocol — 출처 태깅 및 불확실성 처리

이 하네스의 신뢰성은 "어떤 근거로 이 숫자를 썼는가"를 끝까지 추적 가능하게 하는 데서 나온다. 태그를 생략하면 사용자는 이 하네스가 실제 데이터를 본 것인지, 웹서치로 대충 채운 것인지 구분할 수 없다 — 그래서 모든 수치에 태그가 강제된다.

## 출처 태그

| 태그 | 의미 | 사용 조건 |
|------|------|----------|
| `[RAW]` | 사용자가 직접 제공한 원본 데이터 | 항상 최우선 |
| `[OFFICIAL]` | KRX·DART·한국은행 등 공식 기관이 직접 공개한 수치 | 원문 URL·조회 기준일·산출 정의 병기 |
| `[REPORT]` | 증권사·투자은행·자산운용사·헤지펀드 원문 보고서의 표·차트·수치 | 보고서명·발행사·날짜·URL·페이지·원 데이터 제공자 병기 |
| `[WEB]` | 웹서치 결과 | 정성적 맥락(뉴스, 정책, 코멘트)에 자유롭게, 정밀 수치는 아래 4-1 절차 따름 |
| `[DERIVED]` | RAW/WEB을 조합해 계산한 2차 지표 | 반드시 계산식을 함께 명시 |
| `[ASSUMPTION]` | 민감도·스트레스테스트·시나리오를 위해 선택한 가정 | 관측값·역사적 임계값·트리거로 표현 금지 |

WEB 태그를 쓸 때는 항상 원문 출처(매체명, URL, 날짜)를 병기한다. 출처 없는 WEB 수치는 보고서에 쓰지 않는다.

## 보고서 준원자료 증거등급

RAW 시계열이 없으면 공개된 셀사이드·바이사이드 보고서의 **재현 가능한 관측값**을 준원자료로 사용한다. 발행사의 의견·목표가·시나리오 확률은 관측값과 분리한다.

| 등급 | 조건 | 허용 용도 |
|---|---|---|
| **A** | 원문 표에 지표 정의·날짜·수치·원 데이터 제공자가 있음 | 핵심 역사 비교·재계산 |
| **B** | 원문 차트·출처는 있지만 수치 일부를 독해·복원해야 함 | 범위·근삿값, 소수점 정밀도 금지 |
| **C** | 원문이 없고 언론·제3자가 인용한 요약만 있음 | 보조 근거, 단독 임계값 산출 금지 |
| **D** | 발행사의 목표가·임의 스트레스·정성 판단 | `[ASSUMPTION]`으로만 사용 |

보고서 수치는 `[REPORT-A]`처럼 출처와 등급을 결합해 표시할 수 있다. 계산값은 `[DERIVED from REPORT-A]`처럼 원 근거를 유지한다.

## 보고서 증거 추출 규약

각 관측치를 다음 필드로 증거 레지스트리에 기록한다.

```text
claim_id, event, market, metric_definition, observation_start, observation_end,
value_start, value_end, reported_change, frequency, report_publisher,
report_date, report_title, url, page, original_data_provider,
methodology_notes, evidence_grade, source_family_id
```

- **기준일 통제**: 보고서 발행일 이후에 알게 된 값을 당시 판단에 역삽입하지 않는다.
- **정의 통일**: KOSPI/KOSPI200/MSCI Korea, EPS/순이익, FY1/12MF, 주간/월간을 섞지 않는다.
- **중복 제거**: 발행사가 달라도 같은 데이터 제공자·지표 정의·표본이면 같은 `source_family_id`로 묶는다.
- **독립성 보고**: 결론에는 보고서 수와 독립 source family 수를 모두 밝힌다.
- **차트 복원**: 복원 방법·눈금·오차 범위를 기록하고 원문보다 높은 정밀도를 부여하지 않는다.
- **저작권·추적성**: 표·차트 전체를 복제하지 말고 필요한 사실·수치를 페이지와 함께 요약한다.
- **가정 격리**: “EPS 20% 하향 가정”은 실제 하향률이 아니므로 D·`[ASSUMPTION]`으로 분리한다.

## 정밀 수치에 RAW가 없을 때 (4-1 절차)

가격·PER 등 소수점 단위 정밀 수치는 원칙적으로 RAW를 쓴다. RAW가 없다고 웹서치 값을 곧바로 확정값처럼 쓰지 않는다 — 웹 기사는 같은 지표도 서로 다른 숫자를 보도하는 일이 흔하고, 그중 하나를 임의로 골라 쓰면 이후 시나리오 판단 전체가 그 선택에 종속된다.

1. 여러 WEB 소스를 교차검색해 값이 일치하는지 확인
2. 일치하면 `[WEB-교차확인]` 태그로 사용, 출처는 여전히 병기
3. 불일치하거나 출처가 1개뿐이면 `[WEB-미확인]` 태그를 달고, 이 수치가 시나리오 판단(낙관/비관A/비관B 중 어디로 기울지)에 영향을 주는지 판단
   - 영향이 크면 → `NEEDS_CLARIFICATION`으로 팀장에게 보고 (아래 형식)
   - 사소하면 → 보고서 내 "미확인 가정" 섹션에 기록하고 진행

## 상충 수치 처리

같은 지표에 서로 다른 소스가 다른 숫자를 보고하면, 임의로 하나를 선택하지 않는다. 두 값을 모두 병기하고 출처를 명시한다. "코스피 장중 저점: A매체 보도 X pt / B매체 보도 Y pt" 형태로 남긴다. 삭제하거나 평균내지 않는다 — 평균은 새로운 근거 없는 숫자를 만드는 것이다.

## NEEDS_CLARIFICATION 에스컬레이션 형식

작업 중인 에이전트는 사용자에게 직접 질문하지 않는다. 아래 형식으로 자신의 팀장에게만 SendMessage로 보고한다:

```
NEEDS_CLARIFICATION
- 항목: {지표명}
- 상황: {상충/불확실 내용 1-2문장}
- 후보값: {값1 (출처1)} vs {값2 (출처2)}
- 시나리오 영향도 판단: {낙관/비관A/비관B 중 어디로 기울지에 영향을 주는 이유, 또는 "사소함"}
```

팀장은 이를 팀 내에서 조정 가능한지 먼저 시도하고, 안 되면 PM에게 올린다 — 이 판단과 에스컬레이션 로직 자체는 각 팀장의 에이전트 정의(`research-team-lead.md`, `scenario-team-lead.md`)를 따른다.

## 다음 4가지 상황에서는 특히 신중히 판단

1. 동일 지표에 서로 다른 소스가 상충하는 수치를 보고할 때
2. 사용자 제공 raw 데이터와 웹서치 결과가 불일치할 때
3. 분석 기준점(고점/저점 정의, 시나리오 분류 경계 등)이 사전에 합의되지 않았을 때
4. 데이터 공백을 임의로 보간(interpolation)하거나 생략해야 할 때

이 4가지에 해당하면 절대 스스로 확정하지 않는다. 사소하면 "미확인 가정" 섹션에, 중요하면 `NEEDS_CLARIFICATION`으로 보고한다.

## 결론 배제 원칙

리서치 실무자 8명과 research-team-lead, 시나리오팀의 quant-validator·behavioral-finance-observer는 이 스킬을 사용하되 투자 결론("매수해야 한다" 등)을 내리지 않는다. 사실과 1차 해석까지만 서술한다. (시나리오 구축자 3명과 레드팀은 각자의 에이전트 정의를 따른다.)
